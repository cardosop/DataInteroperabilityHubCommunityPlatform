## 2. Staging bring-up root fixes (found live, each TDD-pinned)

The local compose staging stack (the rehearsal target) had been
half-down since 2026-10-07 — `make staging-up` could not complete.
Every blocker below was root-fixed, not worked around:

1. **Staging MinIO healthcheck never passed** — exec-form `CMD` with
   shell operators + a `curl` binary the chainguard image does not
   ship. The test-stack-proven `CMD-SHELL` form (`mc alias set … && mc
   ready local`) is now used; `staging-up --wait` completes. The
   fresh-volume nonroot ownership issue (uid 65532) is documented in
   the runbook.
2. **`prefect-server` failed as non-root** (W8.1 hardening gap):
   `create_ui_static_subpath` materialises the UI build inside
   root-owned site-packages. The Dockerfile now pre-creates + owns
   `…/prefect/server/ui_build` (image-level fix).
3. **The staged `init-db.sql` shipped the TEST-stack role**: the
   `FOR ROLE hub_test` default-privileges lines failed on staging
   initdb, so the admin-alias SELECT grant never applied and login
   500'd with `permission denied for table users`. Root fix:
   `stage_config_artifacts.sh` now substitutes the staging app role
   (`.env.staging POSTGRES_USER` or `--pg-role`; fails loudly when
   unknown) — pinned by
   `TestStagingEnvFileContracts::test_staged_init_db_substitutes_the_staging_app_role`
   (RED→GREEN). The live cluster was repaired idempotently (SELECT +
   DML grants + default privileges).
4. **PgBouncer auth roles missing on the legacy volume** (03 init
   script never ran) — the idempotent script was executed against the
   live cluster; roles + `pgbouncer_lookup()` verified.
5. **`BAAS_DATABASE_URL` carried a stale password** for the same
   `hub_staging` role (direct-postgres baas migrations failed while
   pgbouncer auth worked) — synced to `POSTGRES_PASSWORD` in
   `.env.staging` (values never printed).
6. **Staging email path could never work**: Django 6.1's
   `get_connection()` reads the `EMAIL_*` settings and does NOT consult
   the `MAILERS` dict (verified live: `get_connection()` returned
   host=localhost port=25 while MAILERS named the mailhog relay). The
   settings now mirror `SMTP_*` → `EMAIL_*` in the non-test branch
   (test-runner locmem untouched) — pinned by
   `test_email_settings_mirror_smtp_into_email_vars` (RED→GREEN);
   live verification: `send_mail` delivers into MailHog.
7. **Fail-fast secret registry drift** (W9.2 lane's compose gained
   `JWT_SECRET_KEY` / `ENCRYPTION_KEY` / `SECRET_KEY` without the pin
   list): registered — `TestStagingComposeStaticContracts` 14/14.

## 2b. The scan found a REAL HIGH class — root-fixed, not baselined away

The first plan-driven role scans raised ZAP's SQL-Injection rule
(`40018`, HIGH) with ~70 instances across the authenticated surfaces.
Investigation split it into two classes:

1. **Real 500s on fuzzed integer query params** (RED-proven live):
   `GET /api/v1/governance/certifications/expiring/?days_ahead=10;` and
   `GET /api/v1/observability/pipelines/?limit=;` 500'd with
   `ValueError: invalid literal for int()` — unvalidated
   `int(request.query_params.get(...))` casts. A repo-wide sweep found
   the class across **20 files** (marketplace, scheduled_ingestion,
   billing, contracts ×3, social ×3, analytics, assets ×2, warehouses,
   observability ×6, ai, governance ×2, search ×3, semantic). Root fix:
   ONE canonical helper `hub/apps/core/query_params.py::
   parse_int_query_param` (typed 400 VALIDATION_ERROR, optional
   min/max bounds, empty-string = default) and every unsafe site
   converted with semantics-preserving bounds (the two guarded
   try/except datasets sites left as-is). Pins:
   `test_w1111_expiring_view_rejects_non_integer_days_ahead` +
   `test_w1111_pipeline_dashboard_view_rejects_non_integer_limit`
   (RED-first: both 500'd pre-fix, both 400 post-fix — verified live
   against the rebuilt image too) + the Django-free sweep pin
   `test_no_unguarded_int_query_param_casts_remain` (only the two
   guarded sites may survive). Touched-suite regression: governance
   certs + observability pipelines 13/13; search/contracts/social/
   marketplace/warehouses/semantic suites re-run (below).
2. **Path-param detections with empty evidence** (`«id» AND 1=1 --`)
   — ZAP's OR/AND-based heuristic on endpoints that cleanly 404 the
   fuzzed id (no error reflection, no time delta). Manual reproduction
   showed typed 404 envelopes with no SQL error leakage — recorded as
   scanner false-positives in `docs/security/zap/triage.md` at
   re-baseline time per the triage contract.

All five role scans were RE-RUN against the rebuilt (fixed) image —
the baselines below reflect the fixed tree.

## 2c. Second findings wave — five 500-classes, all root-fixed (2026-10-17)

The fixed-image re-scans surfaced ZAP's `90022 Application Error
Disclosure` (MEDIUM) — five distinct REAL 500 classes (all reproduced
live with a real token, all RED-proven):

1. **UUID-param 500s** (dominant — observability volume/freshness/
   schema-drift/slas + listings): raw UUID query params reached the ORM
   and the `ValidationError` escaped as a 500. Fix:
   `parse_uuid_query_param` (typed 400) in the canonical helper;
   observability views converted (15 sites).
2. **`request.data.get` on non-object bodies** (metrics/schema-drift
   POST): `'str' object has no attribute 'get'` → 500. Fix: dict guard
   (`data = request.data if isinstance(request.data, dict) else {}`).
3. **`search_fields = "name"` — a bare STRING** in files/views.py: DRF
   iterated its CHARACTERS as search fields, so fuzzed search terms
   surfaced `Cannot resolve keyword 'n'` → 500. Fix: `("name",)`
   (source-pinned in the W11.11 suite).
4. **payment-gateways error-path crash**: the exception handler used a
   STDLIB logger with a structlog-style `contract_id=` kwarg —
   `TypeError: Logger._log() got an unexpected keyword argument` — the
   error path itself 500'd, masking the original UUID error. Fix: UUID
   validation at the view + positional/%-style logger args.
5. **Orders-list 500 — stale-DB environment class** (not code):
   `column access_requests.approval_step_records does not exist` — the
   sibling W11.12 migration (governance 0018) was unapplied in the
   rehearsal DB while the rebuilt image expected it; the rehearse-DB
   migrate then hit the RLS role flip (`POSTGRES_USER=meshant_app`)
   vs the legacy table ownership (`hub_staging`). Recorded here as the
   environment class with the fix recipe (apply pending migrations as
   the table owner); the code path is the standard migration flow.

Pins: `test_w1111_volume_view_rejects_invalid_uuid_with_typed_400`,
`test_w1111_record_metric_rejects_non_object_body`,
`test_w1111_gateways_list_rejects_invalid_contract_id_with_typed_400`,
`test_w1111_files_list_rejects_fuzzed_search_without_500` (view suites)
+ `test_files_search_fields_is_a_tuple_not_a_string` (Django-free).
