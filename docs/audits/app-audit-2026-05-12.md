### Async vs Sync Patterns

**Worker:** Gunicorn with UvicornWorker (ASGI). Django views are synchronous (`def`, not `async def`). 0 `async def` view functions found in `hub/apps/*/views.py`.

**Assessment:** Synchronous views on UvicornWorker are the standard Django deployment pattern. The worker handles I/O-bound requests via thread pooling. **Gap:** No dedicated async task queue for long-running warehouse queries. The Athena async polling pattern (ATHENA_POLL_INTERVAL_S=1.0, ATHENA_MAX_POLL_S=300) blocks a gunicorn worker for up to 5 minutes per query. Consider moving to `asyncio` + `aiohttp` for Athena or delegating to an RQ task.

## Audit-Log Forensic Readiness (277.A.26)

**Date:** 2026-05-12

### Incident-Reconstruction Drill

**Scenario:** "Tenant T's asset A was modified without authorization."

**Reconstruction walkthrough:**

| Step | Data source | Query | Expected result |
|------|------------|-------|-----------------|
| 1 | AuditEvent | `SELECT * FROM audit_events WHERE resource_type='ASSET' AND resource_id='<asset_uuid>' ORDER BY created_at DESC` | Who modified it, when, with what action code |
| 2 | AuditEvent (details) | Check `details_json` for `actor_user`, `ip_address`, `user_agent`, `request_id` | Identify actor, source IP, user agent |
| 3 | Logs (Loki/structlog) | Query by `request_id` from step 2 | Full request context, stack trace if error |
| 4 | Traces (Tempo) | Query by `trace_id` from AuditEvent | End-to-end span: middleware → view → service → DB |
| 5 | Auth audit | `SELECT * FROM audit_events WHERE action='AUTH_LOGIN' AND tenant_id='<T>' ORDER BY created_at` | Confirm actor was authenticated, session valid |

**Blind spots identified:**
1. **No `trace_id` stored in AuditEvent.** `create_audit_event()` captures `request_id` (4 refs) but NOT `trace_id`. Trace-audit correlation requires matching by timestamp window, not by shared ID (gap — P1).
2. **No automated incident reconstruction script.** Manual SQL + log queries required. Recommend `scripts/forensic_reconstruct.py` that takes a resource_id and produces the full timeline.

### Cross-Tenant Traceability

**BYPASSRLS audit trail:** `archive_old_audit_events` management command uses `DATABASES["admin"]` (BYPASSRLS) with 5 explicit `.using("admin")` queries. Each query path documented with inline comments.

**`effective_tenant` field:** NOT present in `create_audit_event()`. When a PLATFORM_ADMIN performs a cross-tenant operation, the audit event stores the target `tenant_id` but does not record `effective_tenant` = the tenant being operated on (vs the actor's home tenant).

**Justification field:** NOT present. BYPASSRLS operations should carry a `bypass_reason` in the audit event details dict.

**Gap:** `effective_tenant` + `justification` fields missing from BYPASSRLS audit events. Without these, it's impossible to distinguish "PLATFORM_ADMIN operated on their own tenant" from "PLATFORM_ADMIN operated on another tenant" in the audit log.
