# Image Remediation Runbook — P2-6 (close-oss-release-conditions, G5)

Affected-image remediation: every tag of the published images that
predates the P1 rotations bakes credential material (the tracked
`.claude/settings.json` live bearer token baked by the whole-context
`COPY . .` images, plus the `buildcache` cache-layer tags). Input:
`docs/operations/image-context-audit-2026-10-19.md` (P0-14).

Tool: `scripts/remediate_affected_images.py` (one-shot; Makefile:
`make image-remediation-plan` / `make image-remediation-execute`).
Pins: `scripts/tests/test_p26_image_remediation.py` (CI lint list).

## Preconditions (all machine-enforced)

1. **Rotations complete.** The executor runs the REAL GATE-65
   (`scripts/check_history_rotation_map.py`) before any destructive
   action — while it is red, `--execute` REFUSES and names the
   pending classes. (2026-10-20 state: red on exactly
   `azure-sp-secret`, `stripe-test-key`, `anthropic-auth-token` —
   the three unrotated console surfaces, P1-1.)
2. **A gh token with `read:packages`** (enumeration) **and
   `delete:packages`** (deletion). The keyring token carries neither —
   the live plan run on 2026-10-20 reported HTTP 403 "You need at
   least read:packages scope" for the 9 published packages. Mint a
   scoped token (`gh auth refresh -s read:packages,delete:packages`
   or a fine-grained PAT) before the execution window.
3. **The rotation window-close timestamp** — the RFC3339 moment the
   last rotation landed (from the P1-1 close record). Versions
   created before it are affected. `--execute` requires
   `--window-close <ts>`; without one the run REFUSES.

## Sequencing (the replacement invariant)

1. **Rebuild FIRST.** After the rotations land, run the deploy
   workflow — its P0-14 image-context audit gate refuses
   credential-bearing contexts before any push, and the rebuilt
   `sha-*` tags come from the clean post-scrub context.
2. **Plan.** `make image-remediation-plan` (or the tool with
   `--plan`): enumerates the REAL registry versions and prints the
   disposition plan. A pre-window tag of an ACTIVE package shows
   `REBUILD_THEN_DELETE` until a post-window version of the same
   package exists — deleting the old tags without a rebuilt successor
   would leave deployments without a pullable image.
3. **Delete.** Once every active package carries a post-window
   replacement:
   `make image-remediation-execute WINDOW_CLOSE=<rotation-completion RFC3339>`
   (equivalently `--execute --window-close <ts> --confirm-delete`).
   The deletions go through the real GitHub API
   (`DELETE user/packages/container/<pkg>/versions/<id>`) and are
   IRREVERSIBLE — the `--confirm-delete` flag and the gate order are
   the safeguards.
4. **Record.** The run writes the evidence record
   (`docs/operations/image-remediation-<date>.md`; the 2026-10-20
   record is the honest pre-rotation state) — commit it.

## Disposition rules (pinned)

- `buildcache` tag → DELETE always (BuildKit cache artifact, never a
  deployment target; regenerated by the next build).
- deleted-lane package → DELETE every version (no rebuild possible).
- pre-window tag on an active package → DELETE only with a
  post-window replacement present; otherwise REBUILD_THEN_DELETE
  (the run HALTS, naming the packages).
- post-window version → KEEP.

## The deleted inference-service lane

Delete-or-wire disposition (P2-6): DELETED. The lane never had a
Dockerfile (the deploy workflow guard always skipped it), the helm
chart shipped disabled (`enabled: false`, `replicaCount: 0`), and the
live enumeration on 2026-10-20 reported HTTP 404 for
`datainteroperabilityhub-inference-service` — the package was never
published, so the lane deletion is the complete remediation for it.
The package stays in the tool's deleted-lane list: if versions ever
appear, the plan deletes them. Removed: the deploy workflow lane
(build/meta/check steps, image env outputs, SERVICES entries, digest
output, sign/attest steps, verify-list entry), the helm
`inferenceServing` values block, the four `inference-serving`
templates, the network policy, and the three helm-unittest cases.
The odh-inference-scheduler's simulated endpoint strings still name
`inference-service:8080` — that service is a TEST DOUBLE for the ODH
API (in-memory, dev/test only) and its response shape mirrors ODH's;
the live predict path routes through `run_inference` (P0-16), not
through it. Wiring the lane (a real Dockerfile + service) is Phase
114E feature work, deliberately out of scope for remediation.

## Hazards

- Deletions are irreversible — `--confirm-delete` and the window
  close exist because of this.
- A run with a stale enumeration snapshot can miss freshly pushed
  tags; always plan (which enumerates live) immediately before
  executing.
- The staging stack pulls the `sha-*` tags directly — the rebuild
  step above must complete and be deployed (or at least pushed)
  before old tags are deleted.
