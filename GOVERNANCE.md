# Governance

This document describes how the Data Interoperability Hub project is
governed: roles, decision-making, and the maintenance model.

## Roles

- **Maintainers** — the people with commit access to the repository.
  Maintainers review and merge pull requests, cut releases, and enforce
  the [Code of Conduct](CODE_OF_CONDUCT.md).  The current maintainers
  are listed in [.github/CODEOWNERS](.github/CODEOWNERS).
- **Contributors** — anyone who opens issues, reviews, or submits pull
  requests.  See [CONTRIBUTING.md](CONTRIBUTING.md) for the mechanics.
- **Community leaders** — maintainers acting as the Code of Conduct
  enforcement team.  Reports go to the maintainers' conduct channel.

## Decision-making

- **Consensus with lazy agreement**: maintainers seek consensus on
  substantive changes.  A pull request with two approving maintainer
  reviews and no blocking objections within a reasonable window may be
  merged.
- **Conventional commits** are required on `main` — the release notes
  and the semver bump are generated from them by release-please.
- **Security issues** follow [SECURITY.md](SECURITY.md): private
  disclosure, a fix window, and a coordinated advisory.
- **Architecture changes** (new providers, new boundary seams, new
  enforcement contracts) go through the openspec change process —
  `openspec/changes/` — and must carry specs with verifiable scenarios
  plus the TDD pins that enforce them (the repo convention: claims cite
  a test or a gate).

## Maintenance model

### Release cadence

- **Releases are semver** (`MAJOR.MINOR.PATCH`), generated by
  release-please from the conventional commits on `main`
  (`.release-please-config.json`, `.github/workflows/release-please.yml`).
- **Minor releases** ship continuously: every merged
  `feat:`/`fix:` batch is eligible; the release PR is opened by the
  bot on every push to `main` and merged by a maintainer when the
  checks are green.
- **Major releases** are deliberate: a breaking change requires an
  openspec change, a migration guide entry
  (`docs/migration-guides/`), and the `feat!`/`BREAKING CHANGE`
  commit footer that release-please reads.
- The platform's own components (helm chart `appVersion`, hub `__version__`,
  SDKs, CLI, frontend) all track the single `VERSION` file
  (`scripts/check_release_versions.py` enforces the agreement in CI).

### Support matrix

| Component | Supported versions | Notes |
|---|---|---|
| Python (API, worker, services) | 3.11, 3.12 | dq-service pins 3.11 (soda-core); the rest run 3.12 |
| Node.js | >= 20 | frontend + sdk/js engines floor |
| PostgreSQL | 16 | via pgbouncer transaction pooling in production |
| Browsers | latest Chrome/Firefox/Safari | the E2E suite runs chromium |
| Docker | engine with BuildKit | compose v2 fleet |

Only the latest released version receives bug fixes; the previous minor
is patched for security fixes only during a 30-day grace window.

### OSS security-update SLA

- **Critical/high CVEs in our own dependencies**: a patched release is
  published within **7 days** of disclosure (aimed, not contractual —
  see SECURITY.md for the disclosure process).
- **Moderate/low CVEs**: fixed in the next minor release unless they
  are trivially exploitable in the platform's threat model.
- **Security releases** are ordinary patch releases (release-please
  `fix:` commits) so dependents can upgrade without behavior changes.
- **Support for old releases ends immediately** once a newer release
  ships — no long-term-support branches.

### Dependency & CVE review cadence

The pinned-CVE review process (close-oss-release-conditions P0-2/P0-3)
is a governance commitment, not a workflow side effect:

- **Weekly (automated gate):** `cve-triage-weekly.yml` (Mondays
  07:17 UTC) runs `scripts/audit_pinned_cves.py --strict` — any
  overdue `.trivyignore` review date (or a new entry without one)
  fails the job AND opens/updates the tracking issue
  "Pinned-CVE review overdue (weekly gate)". A lapsed review can never
  sit unnoticed again.
- **Monthly (deep review, 1st of the month 09:00 UTC):**
  `dependency-review.yml` runs the full `pip-audit` pass plus the
  strict audit and opens the monthly tracking issue on findings.
  Maintainers execute the triage procedure in
  `docs/runbooks/cve-triage.md` and commit the wave evidence
  (`docs/audits/cve-triage-2026/`).
- **Escalation:** an open tracking issue older than 7 days escalates
  to the maintenance lead; a Category-C finding (reachable &
  exploitable) is a P0 per the runbook, not a cadence item.
- **Scheduled jobs run only from the default branch's copy of the
  workflow file** — any branch restructure must land the two workflow
  files on the default branch for the cadence to stay live.
